## Сборка для Linux

#### Скачиваем Python
- sudo apt install python3
#### Скачиваем Conan c помощью Python
- sudo pip install conan==2*
#### Создаем папку сборки 
- mkdir build && cd build
#### Подгружаем зависимости которые мы прописали в conanfile 
- conan install .. --output-folder=. --build=missing
#### Строим дерево проекта 
- cmake .. -DCMAKE_TOOLCHAIN_FILE=conan_toolchain.cmake -DCMAKE_BUILD_TYPE=Release
#### Сборка бинарных файлов
- cmake --build .
#### Запуск
Нам нужно будет три терминала в которых мы будем запускать исполняемые файлы
В первом: ./server 9999
Во втором: ./clientB 127.0.0.1 9999
В третьем: ./clientA 127.0.0.1 9999

В папке build/accel появится файл module.log с логами

#### Демон

./build/server --daemon 9000

#### Тесты 

./build/test_protocol


## Реализация в этом репозитории (архитектура, версия протокола, бонусы)

Я реализовал только пункты:
1) Работоспособность Уровня 1
2) Качество кода и архитектура
3) Документация и удобство сборки
4) Дополнительные бонусы(Все)

На освоение gRPC реализацию TLS времени не хватило

Архитектура - это распределенный конвейер обработки данных, где Сервер выступает в роли интеллектуального маршрутизатора и буфера, а Клиенты разделены по ролям: источник/потребитель (Узел А) и вычислитель (Узел Б).

Общий смысл взаимодействия такой:

Узел А начинает генерировать с частотой 50Гц(это каждые 20 мс) данные акселерометра(тут у меня эмуляция) и одновременно с этим слушает входящие данные на сокете

Сервер принимает соединения, идентифицирует клиентов («Handshake») и управляет потоками данных. 

Узел Б принимает пакет данных считает ускорение и отправляет обратно

Из особенностей сервера - это то что он хранит в себе очереди которые отвечают за то чтобы принятые данные не затерялись в случае если один из клиентов отключился. Далее если данные можно отправлять, то вызывается метод send_json по принципу RAII, обеспечивая что метод async_write не будет вызван дважды - использую логический флаг и очередь данных для отправки




**ООП и RAII:** узел Linux — класс `Server` и сессии `A_Session` / `B_Session` / `Base_Session` (разделение ролей, `shared_ptr`, очередь записи в сессии). Клиенты — класс сессии A и цикл B; настройки читаются через `ClientSettings::load_or_default` (RAII-обёртка над файлом конфигурации в `client_settings.cpp`). Также использование std::enable_shared_from_this и std::shared_ptr<> обеспечивает нам RAII принцип

**Версионирование:** во всех JSON добавлено поле `"version": 1` (см. `include/protocol.hpp`). Если поле отсутствует, оно трактуется как **1** для обратной совместимости. Поддерживается только версия **1**; иная версия приводит к ошибке разбора и разрыву логики на узле (исключение / останов цикла).

**Альтернативы формату обмена:** для Уровня 1 выбран **JSON** (текст, отладка «глазами», `nlohmann/json` без отдельной стадии компиляции схемы). **MessagePack** и **CBOR** компактнее и быстрее парсятся, но хуже читаются человеком и требуют библиотеку кодирования на Android и Linux одинаково. **Protobuf** планируется на Уровне 2 (gRPC): строгая схема и меньший размер по сравнению с JSON при потере человекочитаемости по сети.

**Бонусы:** автоматическое **переподключение** клиентов A/B после обрыва (пауза `reconnect_delay_ms` из `client_config.ini`); **частота сенсора** у A — `sample_period_ms` в том же файле; **unit-тест** `test_protocol` (проверка версии и сериализации пакета). Запуск тестов: `ctest` или `./test_protocol` из каталога сборки.

**Демон:** сервер поддерживает флаг **`--daemon`** (только **Linux**, `daemon(3)` из libc). Пример: `./server --daemon 9000`. Рабочий каталог не меняется (`noclose`/`nochdir` выбраны так, чтобы относительные пути к конфигам при необходимости оставались валидными.

**Конфиг:** по умолчанию читается `client_config.ini` из текущего каталога; путь можно передать 3-м аргументом: `clientA 127.0.0.1 9000 /path/to/client_config.ini`.
