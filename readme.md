Тестовое задание: Распределённая система обработки данных акселерометра на C++ (Android NDK + Linux).
1\. Цель задания, сроки
Разработать набор сервисов на языке C++ для трёх узлов (два клиента и один сервер), реализующих передачу, валидацию и обработку данных с датчика акселерометра.
Задание направлено на проверку навыков работы с:

сетевым программированием (TCP-сокеты, gRPC);
сериализацией данных (JSON, Protocol Buffers);
многопоточностью и асинхронной обработкой;
Android NDK и сенсорами (опционально);
базовыми механизмами безопасности (TLS, аутентификация по ключу).
Срок для выполнения задания 2 недели с учетом учебы студентов.

2\. Общая архитектура системы
В системе участвуют три узла:

Узел A (отправитель данных)
Считывает показания акселерометра с частотой ~50 Гц (реальные данные с Android-устройства или эмулированные на Linux).
Упаковывает данные в структуру (timestamp, x, y, z).
Отправляет пакеты на сервер.
Сервер (Linux, Ubuntu 22.04)
Принимает данные от узла A.
Отбрасывает подряд идущие дубликаты (сравнение значений x, y, z с предыдущим принятым пакетом с точностью до 4 знаков после запятой).
Пересылает валидированные данные на узел B.
Узел B (обработчик данных)
Получает данные от сервера.
Вычисляет модуль вектора ускорения: sqrt(x² + y² + z²).
Отправляет результат обратно на сервер.
Обратный поток
Сервер принимает результат от узла B и пересылает его на узел A.
Узел A записывает полученный модуль ускорения вместе с меткой времени в файл (accel\module.log).
Все взаимодействия должны быть реализованы в виде фоновых сервисов (демонов) на C++:

На Android — нативный(С++) код, собранный с использованием Android NDK, запускаемый либо в составе минимального Android-приложения (рекомендуется), либо как отдельный исполняемый файл через adb shell.

На Linux — демон, собираемый с помощью CMake.

Можно выбрать один из двух вариантов развёртывания клиентских узлов:

_Вариант 1: Android + NDK (основной)
_

Узлы A и B — устройства Android (реальные или эмуляторы - можно использовать одну систему, запуская сервисы на разных портах).
Код клиентов пишется на C++ с использованием Android NDK (При необходимости допустима обертка на Java для решения проблем с SEPolicy).
Для доступа к акселерометру используется Android Sensor NDK API. (Допустима эмуляция см. 4.6)
Сборка выполняется с помощью CMake или ndk-build.
Вариант 2: Только Linux (альтернативный)

Узлы A и B — дополнительные машины или процессы на Linux (можно использовать один физический компьютер, запуская сервисы на разных портах).
Данные акселерометра эмулируются в коде узла A (синусоидальный сигнал или случайные значения).
Все остальные требования (сетевое взаимодействие, фильтрация, вычисления, безопасность) остаются неизменными.
Этот вариант допустим, если нет возможности работать с Android, и не приводит к снижению оценки_ при условии качественной реализации всех остальных аспектов.
Во всех вариантах серверная часть работает на Linux (Ubuntu 22.04) и собирается с помощью CMake.

3\. Уровни сложности
Задание разделено на три последовательных уровня. Базовым требованием является реализация Уровня 1. Уровни 2 и 3 выполняются дополнительно для повышения итоговой оценки.

3.1. Уровень 1 (Базовый) — TCP-сокеты и JSON
Транспорт: обычные TCP-сокеты (IPv4).
Сериализация: JSON.

Структура сообщения с данными акселерометра:
{code:json}
{
"timestamp": 1712938123456,
"x": 0.123,
"y": 9.807,
"z": 0.045
}
{code}

Структура ответа (модуль ускорения):
{code:json}
{
"timestamp": 1712938123456,
"module": 9.808
}
{code}

Протокол: каждое JSON-сообщение завершается символом \\n (newline) для упрощения чтения из сокета.

Требования Уровня 1:

Linux-сервер должен обрабатывать подключения одновременно от Android A и Android B (достаточно поддержки одного клиента каждого типа).

На Android A необходимо получать данные от реального акселерометра через Android Sensor NDK API либо эмулировать их (см. раздел 4.6).

Дубликаты отбрасываются только на Linux-сервере (точность 3 символа после запятой).

На Android B модуль вычисляется и отправляется обратно.

Логирование на всех узлах должно быть информативным (подключения, ошибки и т.д.).

3.2. Уровень 2 (Продвинутый) — gRPC и Protocol Buffers
Транспорт: gRPC поверх TCP.
Сериализация: Protocol Buffers (proto3).

Определить сервис в .proto файле с методами:
{code:protobuf}
syntax = "proto3";

service AccelerometerService {
rpc StreamAccelData(stream AccelPacket) returns (stream AccelModule);
}

message AccelPacket {
int64 timestamp = 1;
float x = 2;
float y = 3;
float z = 4;
}

message AccelModule {
int64 timestamp = 1;
float module = 2;
}
{code}

Взаимодействие строится на двунаправленных потоках (bidirectional streaming):

Android A открывает поток к серверу и начинает отправлять пакеты.

Сервер фильтрует дубликаты и пересылает их на Android B через другой поток.

Android B получает поток от сервера, вычисляет модуль и отправляет результаты в ответном потоке.

Сервер пересылает ответный поток на Android A.

Дополнительные требования Уровня 2:

Корректная работа с асинхронным API gRPC C++ (callback API или асинхронный клиент/сервер).

Обработка переподключений и ошибок передачи.

Сборка gRPC для Android NDK (можно использовать vcpkg или предсобранные библиотеки).

3.3. Уровень 3 (Экспертный) — Шифрование и аутентификация
Транспортная безопасность: TLS 1.3 с самоподписанными сертификатами.

Сгенерировать корневой сертификат (CA) и сертификаты для сервера и клиентов.

Настроить взаимную аутентификацию (mTLS) или одностороннюю проверку сервера клиентом (по выбору).

Аутентификация на уровне приложения:

Использовать предварительно распространённый API-ключ (длинная случайная строка).

При установке соединения клиент должен отправить ключ в метаданных gRPC (или в первом сообщении TCP).

Сервер проверяет ключ и разрывает соединение при несовпадении.

Требования Уровня 3:

Самоподписанные сертификаты должны генерироваться скриптом (Bash/Python) и поставляться с приложениями.

API-ключ хранится в конфигурационном файле или зашит в код (для упрощения).

Логирование ошибок безопасности.

### Реализация в этом репозитории (архитектура, версия протокола, бонусы)

**ООП и RAII:** узел Linux — класс `Server` и сессии `A_Session` / `B_Session` / `Base_Session` (разделение ролей, `shared_ptr`, очередь записи в сессии). Клиенты — класс сессии A и цикл B; настройки читаются через `ClientSettings::load_or_default` (RAII-обёртка над файлом конфигурации в `client_settings.cpp`).

**Версионирование:** во всех JSON добавлено поле `"version": 1` (см. `include/protocol.hpp`). Если поле отсутствует, оно трактуется как **1** для обратной совместимости. Поддерживается только версия **1**; иная версия приводит к ошибке разбора и разрыву логики на узле (исключение / останов цикла).

**Альтернативы формату обмена:** для Уровня 1 выбран **JSON** (текст, отладка «глазами», `nlohmann/json` без отдельной стадии компиляции схемы). **MessagePack** и **CBOR** компактнее и быстрее парсятся, но хуже читаются человеком и требуют библиотеку кодирования на Android и Linux одинаково. **Cap'n Proto** даёт zero-copy и эволюцию схемы, но сложнее внедрить в минимальный TCP-поток и тяжелее для учебного объёма. **Protobuf** планируется на Уровне 2 (gRPC): строгая схема и меньший размер по сравнению с JSON при потере человекочитаемости по сети.

**Бонусы:** автоматическое **переподключение** клиентов A/B после обрыва (пауза `reconnect_delay_ms` из `client_config.ini`); **частота сенсора** у A — `sample_period_ms` в том же файле; **unit-тест** `test_protocol` (проверка версии и сериализации пакета). Запуск тестов: `ctest` или `./test_protocol` из каталога сборки.

**Демон:** сервер поддерживает флаг **`--daemon`** (только **Linux**, `daemon(3)` из libc). Пример: `./server --daemon 9000`. Рабочий каталог не меняется (`noclose`/`nochdir` выбраны так, чтобы относительные пути к конфигам при необходимости оставались валидными.

**Конфиг:** по умолчанию читается `client_config.ini` из текущего каталога; путь можно передать 3-м аргументом: `clientA 127.0.0.1 9000 /path/to/client_config.ini`.

7\. Часто задаваемые вопросы
Q: Можно ли использовать Java/Kotlin на Android?
A: Основная логика должна быть реализована на C++ с использованием NDK. Допускается минимальная Java-обёртка для запуска нативного кода.

Q: Обязательно ли использовать реальные устройства Android?
A: Нет, можно использовать эмуляторы Android с включённой эмуляцией сенсоров (через Extended Controls).

Q: Как быть с проблемами SELinux?
A: См. раздел 4.6. Разрешено отключать SELinux на эмуляторе, использовать Java-обёртку или эмулировать данные датчика.

Q: Можно ли собирать Android-часть с помощью ndk-build вместо CMake?
A: Да, это допустимо. Однако использование CMake упростит унификацию с Linux-частью.
